# Production Agent Gateway

The Go Agent Gateway from the public repository [`alexj11324/orvilo-gateway`](https://github.com/alexj11324/orvilo-gateway) at `81f26f8af942484da644921eae08371f834bfd72` runs in a single container, with host port `28787` bound to loopback. Nginx and the proxied Cloudflare hostname expose `https://agent-gateway.aspectlylabs.com` for HTTP and WebSocket clients.

[agent-gateway.yml](../../../.github/workflows/agent-gateway.yml) builds the image on `ubuntu-24.04-arm`; nothing is built on the origin. `build.sh` rejects manual invocation. It verifies the source archive and Go toolchain checksums, runs `go vet` and race tests, builds `orvilo-agent-gateway:81f26f8af942` and saves it into the CI artifact with `start.sh`, `upgrade.sh`, a receipt (commit, source, image ID, binary hash, run) and a SHA256 manifest. Pushes that change this directory or the workflow, and pull requests targeting `canary`, run the build and the `upgrade.sh` test without deploying. No app image is built or changed.

API-key login in both WebSocket versions accepts only `ORVILO_API_BASE_URL`, set to `https://orvilo.aspectlylabs.com` by the launcher. A missing or invalid configured backend URL fails validation. A trailing slash is equivalent; different schemes, ports or paths are rejected before HTTP. JWT authentication remains unchanged. The added unit tests replace the HTTP transport in memory and make no external requests.

First activation on a new origin: load the image from a CI artifact with `docker load`, install its `start.sh` and `build-receipt.json` below `/var/lib/orvilo1/agent-gateway`, the unit in `/etc/systemd/system`, and `nginx.conf` under `/etc/nginx/sites-available/orvilo-agent-gateway` with the matching enabled symlink. Export only the public RSA JWKS from the current production app into `/etc/orvilo-agent-gateway/jwks.public.json`. Create a root-owned mode-0600 `/etc/orvilo-agent-gateway/config.env` from `config.env.example`, filling in the deployment's private Secret Manager project/reference and authorized host user. These references stay on the host. The unit fetches the credential from Secret Manager and creates root-only environment files in `/run/orvilo-agent-gateway` (tmpfs), then runs the nonroot container.

The additive `app.override.yml` is used after the existing production overrides. Recreate only `orvilo` and `hatchet-worker`, with their original image IDs pinned, no pull and no build. Existing `.env` and Device Gateway configuration are retained. The service must start before Compose reads the tmpfs file. Restarting the service loses in-memory gateway sessions; durable conversation history stays in the app database.

To move to a new gateway commit, merge the change in `alexj11324/orvilo-gateway`, then update the commit and archive checksum in `build.sh` and the image tag in `start.sh` (the build fails when the two disagree). After that reaches `canary`, dispatch **Build and deploy agent gateway** from `canary` with `deploy` enabled. Deployment requires this commit's successful `Required Quality Gate` and the `production` environment, and shares the `orvilo1-production-deploy` concurrency group. It transfers the same-run artifact to `/var/lib/orvilo1/agent-gateway/releases/<commit>-<run>-<attempt>` and runs `upgrade.sh activate` there.

`upgrade.sh` checks the manifest and receipt, refuses to start over an unhealthy gateway, and records the installed `start.sh`, the running image ID and its tag under `/var/lib/orvilo1/agent-gateway/upgrades/<commit>-<run>-<attempt>`. It then loads the image, confirms its ID against the receipt, installs the new `start.sh` and restarts the unit. The upgrade stands only if loopback `/health` returns `OK`, an unauthenticated publication is rejected with 401 and the running container is the CI image; otherwise the recorded launcher and image are put back and the unit restarted. CI then checks the public endpoint and restores the same snapshot if that fails. To return to the previous version later, run `sudo bash <release>/upgrade.sh rollback <commit> <run> <attempt>` on the origin. The restart drops in-memory gateway sessions. App and worker containers are not touched: the URL and credential they use do not change.

Before changing app configuration, snapshot the current override and image IDs in a root-only rollback directory. `sudo ./activate.sh rollback` restores that override, recreates app and worker with the original image IDs, disables/stops the Agent Gateway unit, removes only its nginx site, and reloads nginx after `nginx -t`. Remove the Agent Gateway DNS record through the same DNS tool used to create it. The Secret Manager secret can remain as an inactive rollback credential.

Acceptance checks: loopback/public `/health` return `OK`; unauthorized `/api/operations/*` returns 401; invalid v2 JWT closes with 4401; the app public global config exposes this URL and Gateway Mode; app and worker share the correct service credential; a normal authenticated app-issued user token opens v2 and receives events from an authenticated operation publication. Record build source, binary/image digest and the app image IDs in the deployment receipt.
