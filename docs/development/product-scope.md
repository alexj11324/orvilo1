# Orvilo 产品边界

> 本文件是 Orvilo 产品契约的唯一说明位置。当前版本：2026-10-14，来自 [Issue #784](https://github.com/alexj11324/orvilo1/issues/784) 的已确认架构访谈；冲突的旧 Issue、PR 和设计语义由此替代。
> 本文规定目标行为，不表示已经实现、通过验收、合并或部署。未冲突的共享能力继续复用；实现与运行证据须按具体 revision 核对。历史执行记录见 [task-first-rollout.md](./task-first-rollout.md)。

## 一句话定位

面向开发者和小团队的 Agent 交付工作台，以代码交付为主，调研与文档为辅助。独立演进，选择性复用 LobeHub。

Issue 说明要交付什么；Project 组织工作；Agent 执行；Run 记录本次实际发生什么；Checklist、证据与真实 PR 事实证明交付结果。

## 边界原则

> **删除平行的产品形态，不删除执行任务所需的基础能力。**

「不再提供独立图片创作中心」与「Agent 不能生成图片」是两个完全不同的决定。
退役一个入口时，必须逐条追踪 `导航/快捷键/命令 → 路由/懒加载 → UI → store/service → API →
后台任务 → 表/存储对象 → 其他消费者`，覆盖 Web、Electron、Mobile/PWA、Popup、CLI、
内置工具、MCP、分享应用、Workbench、自动化和回调。

每个代码单元标记为：

`DELETE_UI` 专用 UI 删除・`NEST` 下沉・`KEEP_SHARED` 共享能力保留・
`KEEP_COMPAT` 兼容 / 历史读取・`STOP_PRODUCER` 停独立生产流程・
`NEEDS_TRACE` 依赖未确定（**不可直接删**）

优先复用已存在且满足当前契约的能力。GitHub 搜索命中数、同名符号和目录名都不能证明语义等价、归属或可删除；零命中也不能证明 fork 原生。先核对固定 revision 的实现、实际调用者、写入责任和历史读取，再决定复用、迁出或退役。不要为了复用而恢复与当前契约冲突的上游行为。

## 当前交付契约（2026-10-14）

### 1. 产品方向与职责

面向开发者和小团队的 Agent 交付工作台，以代码交付为主，调研与文档为辅助。独立演进，选择性复用 LobeHub。旧实现不自动成为兼容要求；优先解决产品规则、实现和 Agent 指引互相矛盾的问题。

每个工作区配置一个共同的默认 Orchestrator，负责从需求起草计划、Checklist 和任务拆分。编排作为内部工作流，不保留独立的 Goal 产品入口。执行仍遵守发起人的权限。

私聊是需求澄清与任务录入入口。用户只说 “修这个 bug” 而未给具体问题时，先问清楚；需求明确后创建或关联对应 Issue，再由 Orchestrator 制定计划并按依赖调度。交付工作不在私人聊天中直接执行。普通问答和需求讨论仍在聊天中进行。

一个私聊对应一个持续的 session（如 Codex session）。创建或关联 Issue 后原私聊及其 session 保留，不把 “需求转成 Issue” 解释为删除私聊或将整段私聊迁移成 Issue 会话。Issue 执行及 Reviewer 的会话继续按既定运行规则管理。

| 领域         | 职责                                                   |
| ------------ | ------------------------------------------------------ |
| 工作管理     | Workspace、Project、Issue、权限、描述、业务状态        |
| 编排         | 计划、依赖、派发、协调                                 |
| Agent 执行   | 保存的 Agent 配置、设备连接、ACP、Run 生命周期         |
| 验收与交付   | Checklist、证据、Reviewer 结论、人工接受、真实合并事实 |
| 自动化       | 触发规则、周期 Issue、每轮运行与排队                   |
| 辅助生成     | 标题、后续建议                                         |
| 上下文与渠道 | 项目资料、显式会话引用、Slack 接入                     |

这是现有职责的收敛，不要求新建服务或目录体系。只有具体冲突影响当前目标时才拆分或删除实现。

从用户目标出发：Issue 说明要交付什么，Agent 执行，Run 记录本次实际发生什么，Checklist 与 PR 事实证明交付结果。复用现有授权、ACP 原生能力和平台状态；不因每个边界场景增加一套角色、审批流程或状态机。已明确的用户选择优先于参考产品惯例。

### 2. 完整交付流程

需求澄清 → 创建 / 关联 Issue → Orchestrator 起草计划、Checklist 与有向任务依赖图 → 用户确认 → Issue 进入 Backlog → 按依赖约束执行 → Reviewer 检查并提交证据 → 人工逐项或批量接受检查项 → 最终接受交付 → 系统按依赖合并 PR → 一次性 Issue 完成。

所有新代码需求均先确认计划，包括范围清楚的小任务；确认后进入 Backlog，不把确认动作直接等同已开始执行。依赖必须在制定计划时说明：C 依赖 A、B，展示为 A → C 与 B → C，所有前置满足才能放行 C。不得只画图而不约束执行；不允许循环依赖。周期自动化在已确认范围内无需每轮重新确认计划。

确认后的计划由 Orchestrator 自主调度。它按依赖图选择可执行任务；A/B 的前置成果都就绪后，自动推进 C，无须用户再次点击开始、逐层确认或逐项启动。Backlog 表示尚未开始的已确认任务，不能由此推导额外人工启动门槛。

交付目标、Checklist、授权仓库与目标分支、工作范围受用户确认约束。范围内细化子任务、调整实施顺序与合法依赖属于 Orchestrator 的编排职责；不把新增实现子任务自动当作新增需求，再增加一轮审批。越出已确认范围或改变验收要求时才重新确认。任务图与活动记录应反映实际调整。

依赖放行规则：A/B 完成实现和必要检查，代码或产物已可供下游使用后，C 即可基于对应分支继续；无需等待 A/B 最终合并或 Issue Done。全部工作完成后统一接受交付，按依赖顺序合并，最后标记 Done。普通 Run 结束不自动表示前置成果可用。复用同一份依赖关系，区分执行就绪与最终交付完成，不建立第二套 dependency map。

- 独立代码子 Issue 默认各有 PR；有依赖使用 stacked PR，无依赖可并行开发。不强制增加集成分支或最终汇总 PR。
- 支持跨仓库整体交付：父 Issue 统筹同一需求，子 Issue 分别负责不同仓库及各自 PR，沿用整体验收和依赖合并规则。单个执行任务仍可只负责一个仓库。
- 计划确认授予约定仓库、目标分支、工作范围内的后续自动合并权限；最终人工接受交付仍是合并门槛。
- 需求发起人或工作区 Owner 可以接受交付。普通 Issue 编辑权限或 Agent Use 不自动授予此权。
- 代码 Issue 只有在必要审核与 CI 通过、PR 实际合入约定目标分支后才 Done。Agent 声称完成或运行结束都不够；Done 不表示已部署。非 PR 交付按约定标准接受后完成。
- 某个 PR 合并失败，只阻断失败项及其依赖；无关且仍满足审核、CI 和接受门槛的 PR 继续。整组未交付完成时不能标 Done。

### 3. Issue、Checklist 与人工接受

Issue 详情保留 Activity / Checklist 两个相关视图，中文为 “活动 / 验收”。Activity 统一展示评论、状态变化和运行动态，不再增加 “全部 / 评论 / 更新” 分类层。

Checklist 是唯一维护验收标准的地方：Orchestrator 起草、用户确认；Issue 描述承载背景和范围。每项有对应证据和 Reviewer 结论。

采用已选择的 LobeHub 分层：

- 每个检查项可直接接受，也可批量接受；保留逐项勾选确认和全部接受的体验，不另造 “先选择、再提交所选” 的暂存层。
- 机器检查结果、单项人工接受、最终交付接受是不同状态。接受一个或多个检查项只记录验收结论，不自动合并对应 PR。
- 最后点击 “接受交付”，才放行后续自动合并；由需求发起人或工作区 Owner 操作。
- 已接受的普通检查项保留历史结果，新工作不能覆盖旧结果并继承旧勾选；新修改按新的待确认检查项提交。不新增 Git diff 到 Checklist 的自动影响分析。
- Reviewer 失败进入修复流程；无法验证不得冒充通过。证据要对应运行与代码版本。人工勾选不伪造机器通过，也不取消已确认的必要审核与 CI 门槛。
- Reviewer 使用正常配置的 Agent，以保存的设备和模型开启新会话；允许与执行者为同一个 Agent。缺少 Reviewer 时由 Orchestrator 显式指定，不增加工作区默认 Reviewer、父任务隐式继承或平台模型回退。
- 退役旧独立 Acceptance / Verify 产品及引擎，同时保留 Issue 内 Checklist、证据和接受交付能力。

上游参考基准为 lobehub/lobehub\@74d973b51e03d58a1572afd32c2f9ad909fbaf14：单项与组级接受直接写入；普通项人工决定按历史保留，流程生成项另按轮次处理；整体接受是独立动作。我们采用交互与状态分层，不复制上游 “accept 即完成任务” 等与 Orvilo 真实合并门槛冲突的行为。源码调查不等于本产品已完成运行验证。

### 4. Agent、设备与 ACP 权限

只对 Agent 设置使用和管理权限，不增加独立设备共享授权。成员可创建私有或工作区 Agent 并绑定自己的设备；私有 Agent 对其他成员不可见。获准使用共享 Agent 的成员可以在其保存设备上执行，个人电脑仍可承载共享 Agent。

- Agent 保存的设备和模型决定执行；普通使用者不能在会话中覆盖。
- 设备离线明确失败，不静默切换设备。
- 工作区外文件访问限制和强制文件系统隔离留待后续。专用 VM、服务器、SSH 接入不作为本期要求；cwd 不应被描述为安全沙箱。
- 普通交互运行的原生权限模式也保存在 Agent 配置中，仅有管理权限的人可修改。
- 从 ACP 读取实际模式、选项、说明与生效值，并原样设置。Auto/Bypass 不是各 Agent 通用的固定枚举。
- Auto 仍发起权限请求时，在对应 chat 展示原生请求并等待回答；Issue 场景按当前 Agent 的授权与 assignee 范围判断回答资格，有权限的 assignee 均可回答，不固定为原运行发起人，也不另建审批人交接流程。Orvilo 不另造风险判断或统一自动批准策略。
- 普通交互运行中，Agent 自己回退模式时，在聊天中提示实际生效模式，然后继续工作，不额外暂停。Orvilo 不自行选择替代模式。
- 撤销 Agent Use 或工作区成员资格时，请求停止该调用者相关在途任务；收到设备确认才显示已停止。未确认时保留真实的停止中 / 待确认状态。排队项启动前重新授权。
- Slack 和子 Agent 延续发起人身份及 Agent 使用授权，不因转发或委派获得额外权限。

原生工具权限请求的回答人，与最终交付的接受者是两套已明确的职责。

### 5. 周期自动化

同一个 Issue 长期承载周期工作，每次触发产生新的 Run；各轮结果、PR、Reviewer 证据、人工接受记录分别保留。

- 配置并启用时确认持续工作范围；后续在该范围内自动执行，不逐轮确认计划。改变目标或超出授权范围时再确认。
- 所有自动化运行使用原生 Bypass / Full access，覆盖 Agent 保存的普通交互模式。
- 实际 ACP Agent 没有可用原生全放行模式时，不允许用于自动化，配置时明确说明。不静默改为 Auto，也不以客户端自动允许权限请求冒充原生 Bypass。
- Bypass 只改变原生工具权限处理，不取消 Agent Use 检查或每轮人工接受交付。
- 每轮代码交付仍需最终人工接受，再自动合并。PR 合并后本轮 Run 完成，周期 Issue 等待下次运行。
- 同一周期 Issue 按触发顺序串行排队。上轮执行或待接受时保留新触发，交付完成后才开始下一轮；不跳过、不并行、不合并触发。用户已接受可能积压。
- 用户结束整个周期 Issue 后停止后续触发。普通一次性 Issue 的 Done 规则不变。
- 暂停周期自动化停止新触发和排队项启动，保留队列，当前轮继续到交付；停止本轮使用独立操作。
- 单独取消本轮后，设备确认停止且自动化仍启用时，继续下一条排队触发；本轮保留取消记录。

### 6. 会话与项目可见性

- 共享 Agent 的一对一聊天默认仅创建者可见。Agent 使用权不自动授予他人聊天的读取权。
- Issue 内会话遵循 Issue 权限。
- Issue Activity 允许显式 @Agent 或回复 Agent 进入指令入口，普通评论仅讨论。追加执行指令按当前 Agent 授权与任务 assignee 范围检查；不能仅凭普通 Issue 编辑权执行，也不将 assignee 强行解释为单一人类审批人。
- 当前 assignee 可以接续原发起人的同一运行，沿用该运行的执行身份、凭据与环境；负责人变更不自动改写运行身份。此决定针对 Orvilo Issue；Slack 不同成员仍按各自身份建立独立执行会话。
- Project 权限是其 Issue、Run、Checklist 证据的可见性上限；无权访问私有 Project 的成员不能访问其子对象。
- 所有会话引用都遵守相应读取权限。

### 7. 资料、记忆、会话引用与 Slack

采用仓库、本地目录和执行上下文作为项目资源，不提供平台知识库；CLI 如何读取和检索，Agent 通过 ACP 使用其原生能力。保留项目文件、任务附件、产物及共享编辑器。

以任务、评论、历史会话等显式上下文为主，不建设平台自动长期记忆抽取与注入体系；这不授权关闭 CLI 原生记忆或删除历史数据。

- 支持从左侧会话列表拖入其他会话，插入的是引用。
- Agent 按权限按需读取来源当前可用内容。来源更新不自动启动当前 Agent，也不改写已经读取的上下文；需要新进展时再次读取。
- 不增加发送时冻结整段历史的快照模式。
- 首版 IM 渠道为 Slack。现有成员身份绑定、未绑定拒绝执行、不得借用安装管理员身份的规则继续适用。
- **Slack 的外部资料引用来源限当前工作区 Issue 关联的 session 内容，以及获授权 repo 中的文件。Slack 自身的当前 thread 文字和直接上传的附件也作为任务输入。频道和 Slack 私聊都遵守外部引用白名单。**
- 私人独立聊天、未关联 Issue 的其他 Orvilo session，以及外部引用白名单之外的资料，不作为 Slack 引用来源。私人会话引用如需处理，回到 Orvilo；不建议转 Slack 私聊绕过限制。当前 Slack thread 输入与引用其他私人会话是不同来源。
- 允许的来源仍按发起人的工作区、Project/Issue 与 repo 访问权限读取。属于工作区 Issue 或 repo 并不自动免除权限检查。这是 Slack 引用与上下文加载边界，不新增此前明确延后的宿主文件系统沙箱要求。
- 不同成员在同一 Slack thread @Agent 追加要求时，按各自身份建立独立执行会话，不接管原发起人的运行。同一用户可沿自己的会话继续，普通 thread 讨论可作上下文，不因此授予他人执行身份。
- 原生问题和权限请求可在 Slack 回答，回答资格按当前 Agent 与对应任务 assignee 的授权判断；验收证据查看和最终 “接受交付” 回 Orvilo，仍由需求发起人或工作区 Owner 操作。
- Slack 明确的新代码需求自动创建或关联 Issue 草稿，执行前仍需完成既定计划确认；信息不足先澄清，普通问答不自动创建 Issue。
- 目标以明确关联的 Issue / 项目为先，其次频道默认项目 /repo；仍不能唯一确定时询问，不从近期活动猜测。

Marketplace、Skill Store 和平台第三方 MCP 的目录、搜索、推荐、安装、配置与执行管理全链退役；第三方 MCP 与技能由保存的 Agent 对应的原生 Harness 管理。Orvilo 保留内部任务工具及其 ACP 传输、保存的 Agent 配置与直接 GitHub / Linear 集成。其他 IM 渠道不作为首版承诺，退役时仍需追踪历史数据和共享消费者。

### 8. 执行与辅助模型边界

| 能力                                | 归属                                             |
| ----------------------------------- | ------------------------------------------------ |
| 对话、规划、代码执行、Reviewer 审核 | 用户配置的 Agent，通过 ACP                       |
| 标题和后续建议生成                  | 平台统一配置的辅助模型 API；已有原生标题直接复用 |
| 标题存储与展示                      | Orvilo Topic 元数据                              |

生成标题与写回外部会话是不同操作。Codex bridge 已查到 /rename → thread/name/set → ACP 标题通知的可复用路径，仍需真实运行验证；不能把用户观察到无标题直接归因于缺少辅助模型。

### 9. 事实的唯一责任位置

| 事实                       | 唯一责任位置                              | 其他层的职责                                       |
| -------------------------- | ----------------------------------------- | -------------------------------------------------- |
| 要交付什么、验收标准是什么 | Issue 与其 Checklist                      | 描述保存背景；Reviewer 读取同一组标准              |
| 哪项工作依赖哪项工作       | Issue 的真实 blocks 关系                  | 计划图、编排视图和合并排序读取这组关系             |
| 任务如何拆分、何时派发     | 工作区 Orchestrator；现有调度器落实其计划 | 平台校验权限、依赖、已确认范围和执行资源           |
| 设备、模型、普通原生模式   | Agent 保存配置                            | 新 Run 解析配置并记录实际值；旧 Run 保留历史事实   |
| 一次执行正在做什么         | 现有 Run/Operation/Dispatch               | 执行结束只写执行结果，不直接宣布业务完成           |
| 前置成果能否被下游使用     | 具体交付版本及其必要检查结果              | 统一依赖门槛读取它，不要求 Issue 先 Done           |
| 检查是否通过、用户是否接受 | Reviewer 结论与人工决定分别记录           | 不把 Reviewer pass、checkbox、最终接受混为一个字段 |
| PR 是否真的合并            | 仓库提供方与现有合并控制器                | Issue 完成依据目标分支的真实合并事实               |
| 私聊是什么                 | 持续 session、需求澄清和状态沟通          | 创建 Issue 不删除、迁移或公开整段私聊              |

这些责任沿用现有目录与服务，不要求新建服务体系、第二份依赖图或独立状态机。内部编排节点可记录调度、预算和轨迹，不能独立改写 Issue 依赖或完成状态。

### 10. 实现与验证边界

[Issue #784](https://github.com/alexj11324/orvilo1/issues/784) 的源码调查与 PR 状态是调查快照。#750、#768、#774、#779、#782 是候选复用来源；实施前刷新 canary、各 PR head 和实际 diff。open、mergeable、纯函数检查或绿色 CI 都不能证明本契约已在产品中跑通。

按新运行配置与授权 → 完整交付主线 → 周期与跨仓库 → 旧生产者退役的顺序收敛。Checklist、证据、人工接受消费者切换且历史可读后，才移除旧 Goal/Acceptance/Verify 入口与生产路径；同时切换的写入与消费者在同一提交边界，每个合入版本保持可用。不得清空历史代替迁移。

产品验收使用真实 Electron 与对应本地后端，记录 renderer/backend SHA、Agent 保存设备 / 模型 / 实际原生模式、执行版本、结果与证据。不得为了探针覆盖 Agent 的保存配置；云端另记部署 revision。本机不运行 tsgo，Typecheck 使用远端 CI；聚焦 tests/lint 与产品运行证据分别记录。文档契约更新本身不证明产品已实现，也不额外授权生产合并或部署。

## 隐藏产品面退役的判据

> 交付验收对象归属 Issue / Run。独立 Workspace、Agent 与持续私聊 session 仍是有效产品对象；不能按 “没有父任务” 统一删除。

- 退役的是**平行的产品形态**—— 独立验收站点、技能商店、开发者控制台 —— 不是任务执行所需的能力。
- 完成判据不是「导航里没有这个按钮」，而是：从任意入口都无法恢复旧产品，且正式构建不携带其实现。
- 导航不可见**不等于**已退役；只设 `hidden: true` 属于下方「禁止的捷径」。
- 已退役根路径必须保留为保留词，不能被 `/:workspaceSlug` 或 `/agent/:aid/:topicId` 当成业务 ID 解析。
- 平台不得以任何名义（开发工具、内部技能、默认不显示）继续分发已退役的产品面。

## 必须保护的不变量

以下链路不得因功能裁剪而弱化：

- 看板中的同一任务在全局、项目、Agent、「我的任务」中仍是**同一个对象、同一个稳定标识**
- 运行结束**不自动**等于任务验收通过，更不自动等于代码已推送、合并或发布
- 改变看板列不能绕过已存在的完成门控、审批和子任务级联规则
- 已配置的仓库、设备、工作区不可因出错而静默降级到别的执行环境
- 断线、重试、重复回调、迟到回调不得重复创建任务、产物、运行或收费
- 人类负责人和执行 Agent 是不同身份，不相互覆盖
- 权限、工作区隔离、审批、额度、审计、设备身份和访客限制不是「无关功能」

## 禁止的捷径

- 只设 `hidden: true`，旧路由与创建操作照常可达，却宣称功能已删除
- 直接删除 `apps/share`、`ResourceManager`、`generation*`、`memory*`、`document*` 或整个包而没有消费者证据
- 把任务完成列直接映射到「成功」，绕开验收 / 集成状态
- 用新建模拟数据表或 mock 列表替换真正的任务、附件、统计或通知来源
- 为修断链把每个旧链接都重定向 `/tasks` 并丢掉对象 ID
- 把普通成员、Agent、执行操作、外部访客当成同一主体
- 复制源码创建一套「精简版后端」，却让新旧产品同时写同一数据而没有契约
- 对已满足当前契约的能力再写平行实现；未经调用者与语义核对，不能凭搜索结果认定旧路径可删
- 对所有历史用户强制重置偏好，或仅迁移本地而无视远端旧偏好回写
- 为了对齐某份文档快照而回退更新的代码
