### 0.2 已知的方法学限制：本轮**没有**使用 guarded 复核

**这是本文件最大的方法学限制，必须先说。**

已知的坑（团队实测过）：**固定等待会采到「看似合理」的错值** —— 不是采到空，
是采到一个看着完全正常的旧值，所以从读数上发现不了。
而且 \*\*「等稳定」也防不住「长完又长」\*\*：Agent 页实测在 219 个字符处停 4 秒，
终态 435 要 **11–20 秒**才到，团队据此漏掉过整整一块示例区（ref-sweep §8.5 第 7 条）。

**本轮的实际情况（如实标注）：**

| 项                                  | 状态                                                                                                                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 是否用了 `/tmp/guarded-snapshot.sh` | **否**。本轮全部实测均未使用（该脚本 12:05 才出现，我的读发生在知道它之前）                                                                                |
| 我实际用的替代                      | 把 `href` / `docTitle` / **正对照**（`main` 后代计数）写在**同一条表达式内**；参考端 Views 那次另加了「连续 3 次快照一致且 `main` 后代 > 0」的 settle 循环 |
| 是否用了 `/tmp/color-normalize.cjs` | **否**。本文件未做任何颜色比对（只用了字号 / 字重 / 几何），所以该工具的缺失**不影响**本文件任何结论                                                       |
| 是否用了 `/tmp/recheck-overview.sh` | **否**。该脚本是 overview 结构判据，不适用于本文件                                                                                                         |

**为什么仍然可以把这些读数写进本文件**：§0.1 的每一条**都由两条独立路径确认** ——
要么「源码 + 实测」两侧一致（第 2/5/9 条），要么同一事实在两个不同时刻各测一次
（第 1 条 vs ref-sweep 的独立采集）。**单点读数一条都没有被当成事实使用。**
其中参考端 Views 那次**正是靠正对照救回来的**：第一次读数的 `control_mainDescendants: 0`
说明页面根本没挂载，那份「0 视图」是假证据（详见 §8 第 2 条）。

**给下一轮的规则**：本文件所有引用值在**用之前**应当用 `/tmp/guarded-snapshot.sh` 复核一遍。
**采到错值不算错，把错值当事实才算** —— 本节的用途就是让后来者知道哪些格子需要复核。

## 1. 排序判据（先说清楚，否则排序无法审计）

左连接契约是「参考端在该位置有的我们必须有；参考端没有的不许出现在该页」。
按这个契约，排序**不能**只看「差异有多少」，还要看**这份差异现在能不能判**。四个判据：

| 代号              | 判据                                                   | 为什么进排序                                                                          |
| ----------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| **J1 可判定性**   | 每一项 join 现在是否两端都有证据                       | 排序的第一目的是**排工作**。排一个「目标长什么样还不知道」的页面，等于让 builder 去猜 |
| **J2 差异面**     | 差异的元素类数量（双向：缺的 + 多的）                  | 工作量                                                                                |
| **J3 结构性风险** | 差距是否要求改结构（分栏 / 导航 / 状态机），而非改元素 | 结构改动会牵动别的页面与复用件                                                        |
| **J4 复用杠杆**   | 这一页做完是否产出别的页能用的原语                     | 决定顺序的「先做哪个」收益                                                            |

**J1 优先于 J2。** 这是本文件与两份 sweep 排序方法上的根本差别：
ref-sweep 按**参考端复杂度**排，cand-sweep 按**候选端可疑度**排，**两者都不看可判定性**。

另有一条贯穿性的约束：**空态不是正确性证据。**
Inbox / My issues / Reviews 三页的候选端采于空态，其行高、头像、未读点、hover 态
**从未被观测**。这三页在 J1 上一律是「部分」，**不得因为「看起来简单」而排到后面**。

### 4.1 shell 那 9px 对排序**没有信息量**（不得用它排序）

| 分量       | 参考端              | 候选端                                  | 差           |
| ---------- | ------------------- | --------------------------------------- | ------------ |
| 侧栏宽     | **244**（`NAV`）    | **280**（`ASIDE.base-draggable-panel`） | 候选 **+36** |
| 主列左内缩 | **60**（= 48 + 11） | **33**（= 8 + 25）                      | 候选 **−27** |
| 内容列 x   | `244+60 = 304`      | `280+33 = 313`                          | 净 **+9**    |

**三条判据：**

1. **它是两个反向误差的和，不是一处偏移。** 只把内容列挪 −9 会得到
   「304 对上了、但两个分量都更错」的假对齐，且**换个窗口宽度就会分叉**
   （`244+60` 与 `280+33` 对同一次 resize 的响应不同）。来源：ledger 的裁决原文。
2. **它对排序没有信息量** —— 每页等量出现，不区分任何两页。**本文件的 rank 1–6 没有一页
   是因为它而上下的**；§2 的「差异面」列里也**没有一处**引用它（S1/S2/S3 同样如此：
   页标题字号、分段字号、页头高度都是六页等量出现，全部只进本节，不进排序）。
3. **必须在 shell 层一次性决定，不是任何一页的缺陷。** 逐页补偿等于把两个分量各改错六遍。

> ⚠️ **两个未决前提，任何一个成立都意味着 280 不是缺陷：**
>
> 1. **280 可能来自 `DraggablePanel` 持久化的用户拖拽偏好。** 若如此，280 是用户状态而不是缺陷，
>    改成 244 等于覆盖用户偏好。ledger 已就此立规「**在其返回前不得改这个宽度**」。
> 2. **280 可能是候选端自身内容需要的。** 导航是全产品共用的，压到 244 可能截断
>    Linear 没有对应面的那些行的标签。已有一个专门工具在问这个问题：
>    `.agents/acceptance/scripts/nav-budget.cjs`（离线读快照，不占 CDP）。
>    但**它自己声明了不可答的部分**：导航行是**拉伸容器** + `text-overflow: ellipsis`，
>    其宽度是「面板 280」的结果而非需求，所以拉伸行**不给判定**；
>    「在 244 下某行是否真的截断」**无法从快照回答**，需要 `canvas measureText` + 该行的 computed font。
>    **在拿到那个数之前，不得声称它 fits，也不得声称 244 会截断。**
>
> **本文件不预设 280 是缺陷**，也不把这条计入任何一页的排序。

### 5.1 排序结论**正面冲突**

| --------- | ------------------------- | ------------ | ------ |

- ref-sweep 按「**参考端**差异面 × 结构性风险」排 —— 所以 My issues 第一（参考端最复杂）。
- cand-sweep 按「**候选端**一眼可见的可疑之处」排 —— 所以 Reviews 第一（候选端有一处最像 bug）。

### 5.2 两处**必须点名的**误排

**（a）cand-sweep 把 Reviews 排到第 1，理由是「同一句空态连续渲染两次」。**
这条本身是真的（R2，两个独立组件实例 `WorkQueryResults.tsx:364` / `:437`）。
**但它不是左连接差异** —— 参考端 Reviews 页面在**该位置没有对应元素可供 join**，
参考端的分组是 `Ready to merge` / `Created by you` 且**不带计数**，
而候选端那两个空态属于 `In-product approvals` 区块。
修掉这个重复，**parity 推进量为零**。
与此同时 Reviews 真正的差距（双栏 master-detail、行是 PR 不是 issue、分组头缺失、
`For you` vs `For me`）在 cand-sweep 里**一条都没进排序理由**。
**这是把「内部 bug」当成了「parity 差距」—— 两者不是一回事。**

**（b）cand-sweep 把 Views 排到第 6，称「六页里最完整」。**
这正是本任务警告的那个陷阱的**反向形态**：
候选端看起来完整，是因为**候选端有 5 行数据，而参考端一个视图都没有**。
本轮实测确认参考端**至今 `tableCount: 0` / `rowCount: 0`**（§0.1 第 7 条），
所以候选端那 5 行（含 `Layout`/`Sharing`/`Updated` 三列）**没有任何参考物可比**。
Views 实际缺 3 项、多 3 项 —— 差异面并不小，**只是判不了**。
**「看起来完整」在这里是「无法验证」的同义词，不是「做对了」。**

### 5.3 一处**事实性**分歧（引用方须注意）

ref-sweep §4 因 §8.5 回审**修正过 Agent**：初次只看到状态 A（composer 单卡），
漏掉了迟到的状态 B（composer 上移约 91px + 3 张示例卡）。
cand-sweep 对此页没有相反读数，但它把 Agent 记为单一欢迎页态。
**引用 Agent 时必须用 ref-sweep 的修正版（两态），不要用早期读数。**

### 5.4 两处**不构成差异**的候选端不一致（避免误报为 parity 缺陷）

- **空态规格三种**（cand-sweep §7 第 3 条）：参考端自身也不统一 ——
  Views 页级空态是「插画 + 标题 + 正文 + 快捷键 + 主次按钮」，
  Reviews 详情栏空态只有「插画 + 一句 `45 reviews`」，
  Inbox 详情栏占位只有一句 `{N} unread notifications`（无插画）。
  而这些**位置各不相同**（页级 vs 详情栏 vs 未选中占位），
  候选端那三处空态所在的**位置在参考端根本没有被观测到对应物**（参考端这三页都有数据 / 无空态）。
  → 判 **`UNRESOLVED`**，**不是**「空态做窄了」。
- **Reviews 三处空态三种规格**：同上，参考端 Reviews 页无页级空态可对。

### 7.1 对 cand-sweep 提议顺序（Reviews → Projects → Agent → Inbox → My issues → Views）

**裁决：推翻（overturn）。** 三条理由，前两条见 §5.2：

1. **Reviews 排第 1 的依据不是 parity 差距。** 它的依据是一个候选端内部渲染 bug（重复空态），
   而参考端在该位置**没有元素可供 join**，修完 parity 只推进 **0**。
   真实的 Reviews 差距（master-detail、行是 PR、分组头、`For you`/`For me`）没进排序理由。
2. **Views 排最后（「最完整」）是空态陷阱的反向形态。** 候选端「完整」是因为
   参考端 0 视图、比不了。实测再次确认（§0.1 第 7 条）。**判不了 ≠ 做对了。**
3. **把 Projects 排第 2 低估了它。** 它是**六页里唯一两端都有数据、可以逐格判 join 的页面**，
   而排序的第一目的就是排工作 —— 该先做能判的。

### 7.2 对 ref-sweep 提议顺序（My issues → Inbox → Projects → Reviews → Agent → Views）

**裁决：部分同意，仍需修正。** 它对 rank 2/3/4 那个「结构性差异簇」的判断是对的
（My issues / Inbox / Reviews 确实是结构差最大的三页），但它**按参考端复杂度排序，不看可判定性**，
所以把 Projects 压到第 3，而 Projects 恰恰是唯一**现在就能全判**的一页。

### 7.3 本文件采用的顺序与理由

**Projects → My issues → Inbox → Reviews → Agent → Views**

| 序  | 页面          | 一句话理由                                                                                                                                                                                                                                                                                                                                                          |
| --- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Projects**  | 六页里**唯一两端都有数据、每一项 join 现在就能判**的页面；差异是**列形状**的（7 列渲染器 + 1 处表头字符串），一行数据足以判全部 7 列；**且它是唯一能从参考端推出那张共用表格 / 按钮规格的地方** —— Views 与 Projects 现在用的不是同一套（圆角 `999px` vs `6px`、表头 `12/400` 无底 vs `13/500` 浅灰底），但 Views 那侧参考端 0 视图、推不出来，所以规格只能在这里定 |
| 2   | **My issues** | 参考端**最大的、候选端完全为空的**表面（分组 + 父子层级树 + 12 字段行模型），且含六页里最明确的**多出**类左连接违规（5 个参考端没有的页头控件）。注意**不要**指望它的行模型能整块搬给 Inbox / Reviews —— 参考端三页的行语义不同（本页是 issue、Reviews 是 PR、Inbox 是通知），**能复用的是层级缩进与元数据列布局这套原语，不是列模型本身**                          |
| 3   | **Inbox**     | 结构差（master-detail）加 4 类缺失元素，参考端一侧完全可观测；与 Reviews 共用 master-detail 原语，故先做它                                                                                                                                                                                                                                                          |
| 4   | **Reviews**   | 与 Inbox 同一个结构差，外加**语义差**（行是 PR 不是 issue）与一条**最廉价的确定字符串不符**（`For you` vs `For me`）；排在 Inbox 之后**仅因**其详情栏只有空态可观测                                                                                                                                                                                                 |
| 5   | **Agent**     | 差异面**绝对值最大**，但**最不可 join**：候选端的多出项（专属左导航、`WorkingSidebar`、控制条）在参考端**没有可 join 的位置**，关掉它们是**产品决定**不是元素编辑；且与**进行中的 nav 工作流**（`PAGE-INVENTORY.md` B/C 组）耦合，现在做会撞车                                                                                                                      |
| 6   | **Views**     | 缺 3 项、多 3 项都已测准，但**页面主体（有数据的表格）没有任何参考物**。**它现在无法被对齐，只能被阻塞** —— 缺口是「参考端证据」，不是「实现」                                                                                                                                                                                                                      |

### 7.4 排序的前提（决策时必须带上）

1. **rank 2/3/4 三页的 J1 都是「部分」**：候选端为空态，其行模型从未被观测。
   **这三页此时不得被判定完成**，只能判定「已对齐的部分」。
   本排序把它们排在前面，是因为**参考端一侧的证据最全**，不是因为它们容易。
2. **§4 的 shell-level 项必须先一次性裁决**（页标题字号、分段字号、页头高度、
   分段控件元素类型、`aside` 有无、窗口 chrome 是否计入）。
   不先定这些，任何一页的横向坐标都无法与参考端对齐，逐页修必然修出六种结果。
3. **Views 要解开，需要一次参考端写操作**（新建一个视图）才能看到有数据时的形态。
   那是一次**有副作用**的动作，需要单独授权 —— 本轮我没有做。

## 8. 方法学：本轮实测踩到的坑（写给后续采集者）

1. **`location.assign` 深度链接参考端会把渲染进程弄死 —— 连续两次。**
   症状分两种，都出现过：
   - 软失败：标签页停在 `Loading…`，`readyState: complete`，整页只有 **17 个元素**、
     `document.querySelector('main')` 为 `null`。**它不会报错，只会安静地什么都不渲染。**
   - 硬卡死：`Runtime.enable got no response in 30000ms / 45000ms`。
     **恢复**：`curl /json/close/<id>` 关标签，再 `curl -X PUT /json/new?<url>` 开新标签。
     实测软失败那次**会自己恢复**（约 30 秒后标题变成 `Issues`），
     但**不要依赖它**—— 它恢复前你会读到一份「`main` 不存在」的假证据。
2. **正对照救了我一次。** 第一次读参考端 Views 时 `tableCount: 0`、`rowCount: 0`、
   `topBand: []` 看起来是一份干净的「0 视图」证据 —— 但同一份读数里
   `control_mainDescendants: 0`，即**根本没找到 `main`**。
   没有正对照，我会把「页面没加载」当成「参考端 0 视图」。
   **任何「没有 / 是 0」的结论都必须带一个正对照，否则不计。**
3. **参考端标签页集合会变，且不止一个 page target。**
   本轮开始时是 2 个（project overview + `Reviews (17)`），
   期间 `Reviews` 的计数从 18 变 17 —— **数据本身在动**。
   所以引用参考端读数必须带**采集时刻**，且必须 `--match`。
4. **候选端 `:9222` 有别的 agent 在开。** 我的 `--list` 显示 `/my-issues`，
   下一次调用（同一分钟）页面已经在 `/projects`。
   **候选端读数必须带 revision，且两次调用之间页面可能已被换掉** ——
   本轮我因此没能在 My issues 上复核。
5. **沙箱会拒绝含 `location.assign(...)` + 引号的复合命令**（判为「形式太复杂、无法确认是 git」）。
   绕法：把表达式写进文件，用 `--expr-file`。
6. **worktree 隔离下复杂的 `for` 循环 + `git log -1 -- <path>` 会被沙箱拒绝**，
   拆成独立的单条命令即可。
