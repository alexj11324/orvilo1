Static audit of the Orvilo baseline on Linux, 2026-09-30. This identifies reuse points and missing mappings; it does not claim a working production adapter.

## Minimal handoff schema proposal (not applied)

**One new table; two additive columns on the canonical run table. No new live-authority table.** This proposal reserves no migration number and does not change schema files.

Add `task_topics.execution_control` nullable typed JSONB and `execution_control_revision` nonnegative integer default zero. Existing `execution_epoch` and `execution_grant_id` remain the only authoritative epoch/grant; do not duplicate them in the new live aggregate. Null control means an unmanaged legacy run, not permission to execute new Core actions. Preserve `task_topics.handoff`, which already stores an LLM-written completion summary. Do not reuse `agent_operations.metadata`: it has generic writers and no demonstrated trusted-only mutation boundary.

The execution-control aggregate contains:

- `schemaVersion: 1`.
- `ownerId`: host-assigned execution owner identity, unrelated to provisioning leaseOwner or human principal.
- `leaseId`: fresh opaque fencing ID; `leaseExpiresAt`: finite database-checked timestamp.
- `state`: `registering | running | held | stopped`.
- `registrationId`: immutable host launch idempotency identity for this occupancy.
- `supervisorId`, `treeId`, `sessionId`: nullable until trusted registration succeeds; all required before running admission.
- `activeHandoffId`: null or the durable handoff intent holding mutation admission.

Use constraints to require complete identifiers in `running`, a nonempty handoff ID when handoff-held, valid timestamp/version/state shapes, and no implicit fallback for malformed JSON. The revision increments on every registration/hold/lease/transfer/state change; expiration renewals must validate exact owner/lease/epoch and current grant. Store tree identity, not credentials or provider endpoints. The run row is the serialization point. JSONB is suitable as a small typed aggregate only if all writers use the trusted repository and database row lock/CAS; generic metadata updates are not an acceptable substitute.

Add `task_execution_handoffs` for durable history and recovery:

| `successor` JSONB nullable                         | Immutable transfer result fence/lease/registration identity for recovery, not an alternative authority row. Current permission always reads task_topics.         |
| `created_at`, `updated_at`                         | Audit timestamps.                                                                                                                                                |

Constraints: phase/version/revision checks; one nonterminal handoff per task via a partial unique index; same ID + different intent rejected. Retain terminal records so old IDs cannot restart a different handoff. Avoid cascade deletion for new audit history until the repository's soft-delete/purge retention policy is explicitly mapped. A FK to task_topics with RESTRICT is an option but must be reviewed against existing user/workspace deletion cascades; this is a concrete migration decision still open.

### Atomic lifecycle

1. **Initial registration:** trusted admission locks task and canonical run; validates current task/dispatch/operation/grant/delegation subject and revisions; claims canonical execution epoch and a new owner/lease/registration ID with state registering. A supervisor idempotently ensures one tree for that registration. Persist its binding and open running admission only after reauthorization. A crash never authorizes launching an unrelated replacement using the same registration.
2. **Begin:** lock task then run using the same global lock order as other writers; validate owner/lease/epoch plus task and membership/policy authority; insert handoff intent and change run to held/activeHandoffId in one transaction. Keep source owner/lease identity. No mutations may enter after the hold.
3. **Quiesce:** outside the database transaction, supervisor stops the entire source registration and drains all admitted actions. Persist proof by CAS. Expired source lease or a stale proof does not justify reopening source admission.
4. **Transfer:** lock current task/run/grant/required authority rows; require held state and matching source/intent, zero pending actions and currently verified supervisor proof. Atomically increment existing task_topics.executionEpoch, change owner to successor, issue fresh lease and registration ID in registering state, increment control revision, and mark history transferred. Never assign null owner. Source lease expiry during quiescence must have an explicit reauthorization/recovery rule; it cannot silently grant transfer.
5. **Resume:** ensure exactly one successor tree under the persisted registration ID, revalidate lease/grant/policy, bind the tree, clear activeHandoffId and open running admission while marking resumed in the same transaction. A retry reuses the registered tree; it never calls ordinary non-idempotent start.

### Blocking integration work

This schema alone does not provide handoff. Required before production activation: durable supervisor registration/recovery by registration ID; task/run owner lease lifecycle; action admission/drain sharing the run lock; updates to existing claimExecutionEpoch, revoke, cancellation and runtime completion paths so legacy writers cannot bypass the hold; current membership/policy/deletion reads under a coherent locking strategy; task/current dispatch/operation mapping; cleanup for crashes before/after supervisor launch; database-backed negative and crash-recovery tests. Grant ID stays unchanged only if the successor owner is authorized under the same grant; switching agent/principal requires explicit policy and contract support, not this owner's string replacement.

Core `ExecutionFence.stateRevision` must have an explicit mapping: use `execution_control_revision` for the occupancy CAS, while separately validating canonical task domain/requirement/policy revisions from task/run rows. Do not silently map both task domain revision and control revision to one value. If consumers currently require stateRevision to mean task.domainRevision, keep that meaning and add a separately bound control revision in trusted repository context; decide this contract mapping before implementation.
