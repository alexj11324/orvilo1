# Workspace permissions

The approved policy separates ordinary workspace collaboration, Project governance, Agent execution and Device access. The server is the authority; UI capabilities describe permitted actions and default to disabled while loading or after a failed permission request.

This document describes the permission candidate prepared on baseline `f81bd916e59a6256651ac4301962b8afb7b6e9fd`. It does not claim that the cloud deployment or Electron runtime has adopted it. The capability table, boundary rules, source map and rollout gates below state the approved policy and its acceptance requirements.

## Policy

Every workspace action checks the actual caller, selected workspace, current active membership and workspace role ceiling. Owner, Admin and Member can write; Viewer can read. Suspended, removed and foreign-workspace callers cannot use historical ownership, manager labels or grants to regain authority. Personal resources retain owner scope.

| Capability                             | Rule                                                                                                                                                                                                                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project, Issue and Issue dialogue read | Active workspace members can read the unified workspace model. Legacy private Project records retain their existing read boundary until separately approved publication. Issue dialogue is workspace-readable independently of Project participation and private Team membership. |
| Ordinary Project/Issue collaboration   | Writable workspace members create and edit ordinary fields, dates, milestones, associations, updates and comments without joining the Project. Existing completion approval, review lifecycle and run fences still apply.                                                         |
| Comment text edit                      | Only the recorded author with current writable authority. Manager, Lead and administrator cannot rewrite another author's text.                                                                                                                                                   |
| Comment delete                         | Writable author; workspace governance; Project manager for comments within that Project. Existing deletion/audit paths apply.                                                                                                                                                     |
| Project governance                     | Active Project manager or workspace Owner/Admin manages participants, roles, settings, deletion and completion approval. Creator receives an initial manager row when active and writable. Lead/assignee expresses responsibility.                                                |
| Issue delete                           | Active writable Issue creator, its Project manager or workspace Owner/Admin.                                                                                                                                                                                                      |
| Agent safe profile                     | Active workspace membership permits safe profile reading; legacy private profile material and full configuration remain restricted pending reviewed publication. Issue-linked identity does not expose private instructions, welcome text or credentials.                         |
| Agent configuration and Use roster     | Active writable creator or workspace Owner/Admin can manage. Management does not grant execution. Use alone does not grant configuration or deletion; existing dependency and running-reference constraints remain.                                                               |
| Agent Send/Run/Answer/Pause/Stop       | Current explicit per-user `use` row plus workspace execution ceiling and existing Group ceiling. Creator receives an initial removable row once; cancellation is never restored by a read or bootstrap. Admin, global edit, Project participation and assignee do not imply Use.  |
| Device read/files                      | Existing caller-owned personal or visible workspace private/shared registry plus approved directory. Viewer can read eligible files but cannot write or execute.                                                                                                                  |
| Agent execution on Device              | Actual Agent Use, actual caller Device authorization, matching installed and online/ready runtime, and approved directory. Agent creator identity cannot substitute for the caller.                                                                                               |
| Direct Device file mutation            | Device visibility, current writable workspace ceiling and approved directory. These RPCs have no Agent ID and do not assert Agent Use.                                                                                                                                            |
| Device management                      | Existing enroller/workspace-owner conditions and writable ceiling. Admin receives no additional Device-management authority.                                                                                                                                                      |

Project identity choices are Participant (`contributor`) and Manager (`manager`). Existing historical `commenter`/`viewer` rows remain stored until approved conversion. No new role engine, Device ACL roster or permission table is introduced.

Project Manage never supplies Agent Manage. A distinct Project manager can delete the parent while its coordinator, session and history remain. Creator/Admin cleanup requires independent Agent Manage and the existing live-operation and dependency guards; known builtins and Agents reused by another Project or Group remain. There is no automatic orphan cleanup.

Without Agent Use, members retain readable Issue dialogue and ordinary Issue comments. Send, Run, Answer, Pause and Stop remain visible and disabled, and the server rejects attempted execution. Permission changes reuse existing capability caches, membership events and authorization versions; stale UI does not authorize the next action.

New actions, locked queue dispatch, durable start, resume and scheduler/heartbeat entry recheck the recorded initiator and actual executor. Missing initiators do not fall back to creators or audit strings. An already-authorized original producer can complete through its original valid operation principal, token, grant and epoch after Use-row revocation. Current principal validity still applies; stale epochs and duplicate terminal callbacks remain rejected. This does not promise immediate termination of an external OS process.

Device selection counts authorized devices with known matching installation evidence, including offline matches. One settled match auto-selects and hides the picker; two or more show it. Unknown scans do not establish a singleton. Offline/readiness independently disables Run. Index/search stays within the requested approved subtree; repository operations also validate the native effective Git root and destination roots.

Document, KB and attachment content keeps its own resource ACL. Shared Issue DTOs and linked identities must not publish configuration secrets, session/runtime credentials, private paths or historical snapshots. Workspace Issue visibility does not authorize historical private-content publication.

Competitor references explain principles; they do not replace the approved Orvilo rules. The inspected immutable Multica sources separate [invocation, view and management](https://github.com/multica-ai/multica/blob/e0f84dda47d42f1826af6b8f596de0b38c3d90a6/server/internal/handler/agent_access.go#L73-L256), restrict [Access edits](https://github.com/multica-ai/multica/blob/e0f84dda47d42f1826af6b8f596de0b38c3d90a6/server/internal/handler/agent.go#L1998-L2043), and enforce [runtime-owner predicates](https://github.com/multica-ai/multica/blob/e0f84dda47d42f1826af6b8f596de0b38c3d90a6/server/internal/handler/runtime.go#L863-L903). This is evidence for those selected files at that commit, not every permission file or a deployed service. Orvilo deliberately differs: creator Use is revocable, workspace administrators can manage the Use roster, and no-Use users cannot control execution.

The pinned Plane Community [Project creation branch](https://github.com/makeplane/plane/blob/5f7d92784c403f76284f0f16718f320221dc7fec/apps/api/plane/app/views/project/base.py#L225-L280) promotes a selected Lead to Admin, while its [comment mutation branch](https://github.com/makeplane/plane/blob/5f7d92784c403f76284f0f16718f320221dc7fec/apps/api/plane/app/views/issue/comment.py#L109-L158) admits Admin or creator. Orvilo's approved policy instead keeps Lead informational and text editing author-only; these source branches are not an Orvilo parity requirement or proof of competitor runtime behavior.

## Evidence and rollout gates

The four task reports record focused RED/GREEN regressions, scoped lint, PGlite/model tests and native temporary-Git tests. Independent task reviews and bounded repairs assess source behavior. This documentation does not rerun or independently approve those checks. The integrated drift review and exact delivered-revision remote CI, including Typecheck, remain required; local tsgo is prohibited.

Real acceptance requires the candidate Electron renderer against the intended cloud backend. Record renderer and deployment SHAs separately, then attach outcomes/screenshots/logs to the delivery PR or Actions artifact. Use authorized real Owner/Admin/Member/Viewer actors and a dedicated approved resource/Device/directory envelope. Cover ordinary nonparticipant collaboration versus governance, author edits/deletes, inactive/foreign denial, Admin Manage without Use and creator self-revoke for all five execution controls, queue replacement/revocation and resume/heartbeat, valid producer terminal versus stale/duplicate callbacks, personal/shared Device and directory denial, Viewer file writes, zero/one/two/offline/unknown runtime selection, Retry/reconnect/reload and retained Electron tabs. Those actors/resources and complete outcomes are pending; existing Owner getter evidence on backend f81 is narrower.

Historical data changes require a fresh metadata-only preview with exact workspace/resource/owner/member/grant IDs and reviewed snapshots. Do not export private bodies or configuration. Obtain separate per-record publication and legacy-role/grant conversion approval; policy approval or prior local-clone approval does not authorize cloud apply. Unapproved private Projects/Agents keep their boundary; associated workspace Issues retain the approved shared rule. Doc/KB/attachment/history publication remains separately scoped.

The migration tool defaults to dry run, separates permission conversion from publication, rejects snapshot drift, preserves global rows, and claims an exclusive mode-0600 receipt binding the plan before apply. Consumed plans cannot replenish revoked grants. Before authorized apply, verify actual deployed schema and fresh approved snapshots, then exercise real PostgreSQL transaction/concurrency/rollback behavior; PGlite alone does not prove multi-connection locking. No historical apply or publication has been accepted. Do not merge/deploy or mark runtime/migration acceptance complete until the corresponding gates have evidence for the delivered revision and approved scope.
