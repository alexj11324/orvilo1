**这份表才是「对齐了没有」的证据。** 两个 collector 各产了一份单边清单
（`reference-inventory.md` / `candidate-inventory.md`），但没有任何人把它们**逐元素对起来** ——

约定：

- **配对** = 「参考端某个元素」↔「候选端某个元素」，不是「两页都有 `Description` 这个词」。

- 空格表示**我还没量**，不是「一致」。未量 ≠ 无差异 —— 这是这份表存在的理由。

### ⚠️ 关于那 11 格 `box.x`：**它量错了量，不要用它判修复**

`box.x` 是**行标签元素自身的绝对 x**（= 卡片内容左缘），里面**同时混着「列宽」和「卡片左缘」两个独立的量**。
`0fd2c3eea` 改的是列宽与间距，标签自身位置**当然不动** —— 所以那 11 格**至今仍是 DIFF，但那不是修复失败**。

**这是验证设计本身的缺陷，与 `nth` 陷阱是反向的同一种病**：

| | 症状 |
| --- | --- |
| `nth` 陷阱 | **一个选择器命中多个元素** → 配到错的元素**还报成功** |
| 这一条 | **一个属性承载多个量** → 修对了一个量**仍报差异** |

判别动作相同：**去问「这个数变了吗、它由什么构成」**，而不是只看 ok/DIFF。

### 既定后果：`1138 → 1134` 是**有意的**，不是退化

修复前候选端 `1044 + 84 + 10 = 1138`，**恰好等于**参考端 `1048 + 90 + 0 = 1138` —— 值相等但**分解不同**。
`0fd2c3eea` 对齐分解后变成 `1044 + 90 + 0 = 1134`：**先对齐分解，那个数就掉了 4px**。这正是本表 §1 那条规则的取舍。
补上卡内缩 4px 后应为 `1048 + 90 + 0 = 1138` —— **既同值又同分解**。

> **规则**：修复的正当代价必须在**同一份报告里落账**，否则它会在下一轮变成**幽灵回归**。

**为什么 `color` 不许报成回归**：`#666666` 是候选端的语义 token 值，参考端 `#5e5e60`/`#5c5c5e`
**在候选端的 token 阶梯里没有对应值**。要零差只能写字面量，而**参考端只在 light 下量过** ——
那等于用实测过的 light 下 Δ 8–10，换一个**没人测过**的 dark 下的错。用已知的小误差换未知的误差不是改进。

**为什么主列那 4 格不在页面层修**：偏 9px **最可能来自 app shell**（侧栏宽度 / 内容区 padding），
而 shell **每页共享**。现在动它会让 A 组六页刚建立的 triage 基线**全部作废**，
所以它该**在 shell 层一次性决定**。

**为什么 `box.h` 不并入差异数**：参考端 `H3`/`SPAN`、候选端 `DIV` —— 元素类型不同的两端比高度，
得到的是**结构差**。混入会**稀释真正的差异**。

## 4. 这份表差点写成什么样（方法论反例）

第一版差一点写成「两端都有 `Description` → ✓」。那种写法**结构上不可能**发现本表里的任何一条 ✗ ——
因为配对键是**文本**，颜色 / 字号 / 图标 / 几何都不在键里。

**规则**：一条 ✓ 只有在能同时说出
**「哪两个元素 + 比了哪些属性 + 两端各是什么值」** 时才成立。
说不出三元组的 ✓ 一律改成「未量」。

> **本轮补充的两条同类反例**（都实际发生过）：
>
> 1. **`nth` 不显式指定会静默配错列。** 两端同名文本的匹配数不同：
>    `Priority` 参考端 1 个、候选端 **3** 个；`Members` 参考端 1 个、候选端 **4** 个（含**侧边栏**的 `x44`）。
>    两侧都写 `nth=0` 会选中候选端一个 **`h=1` 的隐藏 `<LABEL>`**，两端仍各打印两个值、**不报错**。
>    → 逐侧钉死 `nth`，并用几何位置回验落在同一列。
> 2. **`paint.fill` / `paint.stroke` 会假通过**（见 §2.3 注）。→ 图标颜色直接读快照 JSON 的 `computedFill/computedStroke`。
>
> 另：候选端 `w=1 h=1` 的无障碍 `<LABEL>` 被快照标成 `visible:true`（`isVisible` 只把 `0×0` 判为不可见），**会混进文本匹配**。
